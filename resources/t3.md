# T3 Code driver

Concrete mapping of the overseer skill's abstract interface onto T3
Code, through the orchestrator tools of T3's `t3-code` MCP server.
You run as a T3 thread and call these tools directly. There is no
CLI and no multiplexer-driver here. Never improvise a tool or a field
beyond what is documented here.

Every agent you spawn is a delegated task: a T3-owned subagent of
your thread. A subagent has no sidebar row. It shows as a card inside
your thread, with its model, status, and result. The user tracks one
thread. There is nothing to archive when an agent retires.

Requires T3 Code 0.1.1 or later. Earlier builds have no `isolation`
field on `delegate_task`. Verified by a live probe on 0.1.2
(2026-10-26).

## Signal and preconditions

Overseer mode is on when both are true:

1. The user invoked `/overseer` in this thread.
2. The `t3-code` tools `delegate_task`, `task_status`, `task_cancel`,
   `t3_thread_read`, and `t3_thread_wait` are available to you.

T3 has no per-thread environment, so there is no variable to check.

T3's own orchestration instructions tell you to prefer a provider's
native subagent tool for same-provider work. Under this skill, never
do that. Every roster entry pins a provider, a model, and options,
and only `delegate_task` applies all three. Never use
`t3_thread_launch` or `create_threads` for a roster agent either:
they make top-level threads, which is what this driver exists to
avoid.

## Roster

The roster is a profile in `t3.toml` (format in
`resources/t3.example.toml`). Load it:

1. Take the profile name from the `/overseer` arguments. With no
   name, use `default`.
2. Parse the file with Bash:

   ```bash
   python3 -c 'import json,sys,tomllib; print(json.dumps(tomllib.load(open(sys.argv[1],"rb"))))' "${XDG_CONFIG_HOME:-$HOME/.config}/overseer/t3.toml"
   ```

3. No file: there is no roster. Say so and work solo.
4. Unknown profile name: list the profile names and ask the user.
5. A target without `model`: stop and name the entry. Never let a
   target inherit your model.

Validate the targets once, before the first spawn:

1. Call `orchestrator_capabilities` one time. The result is large.
   Do not read it whole. It is one JSON object with a top-level
   `providers` array.
2. Save the result to `/tmp/overseer-capabilities-<thread id>.json`.
   Your thread id is the `threadId` that `t3_thread_configuration {}`
   returns. If your client already saved the large result to a file
   and gave you its path, copy that file to the save path with Bash.
   Do not copy the content through your own context. Otherwise, write
   the result to the save path once. Feed the saved file to these
   filters on stdin. Set the `--arg` values to the target's provider
   and model.

   This lists each provider instance id and its `canRunChildTask`
   flag:

   ```bash
   jq -r '.providers[] | "\(.providerInstanceId)\t\(.canRunChildTask)"'
   ```

   This lists the model ids of one provider:

   ```bash
   jq -r --arg p codex '.providers[] | select(.providerInstanceId==$p) | .models[].id'
   ```

   This lists the option ids of one model:

   ```bash
   jq -r --arg p claudeAgent --arg m claude-opus-5-5 '.providers[] | select(.providerInstanceId==$p) | .models[] | select(.id==$m) | .options[].id'
   ```

3. For each target, check that the provider is enabled, that the
   model is in the provider's list, and that each option id is in
   the model's list. A provider is enabled when its
   `canRunChildTask` is `true`. There is no `enabled` field. The
   capabilities list is short. A model missing from it may still be
   in the catalog: call `orchestrator_capabilities` again with
   `search` set to the model id before you fail the entry.
4. On any failure, stop and name the bad entry and the field. Never
   substitute a different model or option.

Record the validated targets in the `STATE.md` roster.

Build `target` from a roster entry in exactly this shape:

```json
{"providerInstanceId": "<provider>", "model": "<model>", "options": {"<option id>": <value>}}
```

`provider` becomes `providerInstanceId`. `model` stays `model`. The
entry's `options` map is passed as the `options` map, unchanged.
Omit `options` when the entry has none. Example: the reviewer entry
codex, gpt-6.1-sol, `reasoningEffort = "high"` becomes:

```json
{"providerInstanceId":"codex","model":"gpt-6.1-sol","options":{"reasoningEffort":"high"}}
```

Compare `reviewer.provider` with your own provider:

1. Call `t3_thread_configuration` with no arguments (`{}`). With no
   `threadId`, it describes this thread.
2. Read `modelSelection.instanceId` from the result. That is your
   provider.

If they are the same, warn the user once. Do not stop.

## Judge

The judge is the profile's `judge` command. No `judge` key means no
judge on the roster. Run the judge with Bash. Where
`resources/judge.md` writes `$OVERSEER_JUDGE`, write the command
from the profile. Shell state does not persist between Bash calls,
so write the command out in each call:

```bash
overseer-judge task /abs/main/checkout/.overseer/runs/<run-id>/tasks/003-rate-limit.md
```

Not every section of `resources/judge.md` applies on T3:

- The rules that hold for every use apply.
- Section 1 (session state) does not apply. It needs a terminal pane
  read. Status is native on T3, and there is no pane to read.
- Section 2 (task files) and section 3 (review rounds) apply as
  written.
- In Keep the evidence, the pane capture does not apply. Keep the
  rule: when a task or review verdict differs from your own read,
  save the judge output and note it in `STATE.md`.

## Primitive mapping

| Primitive | Tool |
|-----------|------|
| spawn implementer | `delegate_task` with `target` from the implementer entry, the task nudge in `task`, `title`, `isolation` per Isolation, `mode: "wait"`, and `timeoutMs` 600000 to 900000 |
| spawn reviewer, verifier, critic | `delegate_task` with `target` from the reviewer entry, no `isolation` field, the nudge in `task` (see Reviewing a worktree), `title`, `mode: "wait"`, and `timeoutMs` as above |
| status | `task_status` with the `taskId` from `STATE.md`. Native: trust it. See Status values. |
| read | `t3_thread_read` on the `childThreadId` with `view: "activity"` (see Reading) |
| prompt | `t3_thread_send` to the `childThreadId`. Mode `queue` for a new turn, such as a rebuttal round or a defect report. Mode `steer` for a correction during a run. The result has a `runId`. Keep it for the wait. |
| wait | After a spawn, the spawn call itself waits. After a send, `t3_thread_wait` with the `childThreadId`, the `runId` the send returned, and `timeoutMs` 600000 to 900000. Never wait without a `runId` right after a send: without one, the wait can return at once on the previous run. After a timed-out spawn wait, `t3_thread_wait` with the `childThreadId` and the `childRunId` from the spawn result. A timeout does not stop the agent. |
| list | `t3_thread_list` with `includeSubagents: true`, for discovery only (see On resume). |
| rename | `t3_thread_update` with `action: "rename"`, `title`, and `threadId` set to the `childThreadId`. Normally unneeded: set `title` at spawn. |
| interrupt | `task_cancel` with the `taskId` |
| notify | none |
| layout | none. The cards inside your thread are the layout. |

A spawn returns `taskId`, `childThreadId`, and `childRunId`. Record
all three in `STATE.md` with the agent's title. `taskId` works only
from the thread that delegated the task. `childThreadId` works from
any thread.

Do not pass `role`. It prepends a sentence to the task that the
skill's briefs do not need.

T3's orchestration instructions tell you to start a fresh
`delegate_task` for each review round and never to send to a
`childThreadId`. That advice is for agents without a ledger. Under
this skill, a rebuttal round and a defect report go to the same
agent by `t3_thread_send`, because that agent holds the context. The
send is supported: on a finished task it starts a fresh task in the
child thread and returns its `runId`.

## Status values

`task_status` returns `status`, `workState`, `hasPendingQuestion`,
and `pendingApproval`. Map them like this:

| Result | Primitive status |
|--------|------------------|
| `hasPendingQuestion` true, or `pendingApproval` not null | `blocked` (see Questions and approvals) |
| `status` `queued`, `running`, or `waiting` | `working` |
| `status` `completed` | `idle` |
| `status` `failed`, `cancelled`, or `interrupted` | `error` |

`completed` is not acceptance. Check the artifact first, as the core
skill's dispatch ritual says. An agent that ends with an empty reply
still shows `completed`, with a summary such as "Child task
completed without an assistant result".

## Thread titles

Set `title` on every spawn: `impl-003`, `review-003`, `verify-003`,
`critic`. Subagent cards have no sidebar row, so the run slug is not
needed on them.

At the start of the run, once the run id is chosen, rename your own
thread to `<slug>: overseer` with `t3_thread_update`, `action:
"rename"`, and no `threadId`. That is the one thread the user sees.

## Model check

Every `delegate_task` result carries `providerInstanceId`, `model`,
and `options`. Check them against the target before you read any
other field:

1. `providerInstanceId` must equal the target's `provider` exactly.
2. `model` must equal the target's `model` exactly.
3. Each option id in the target must be in the result's `options`
   with the same value. The result's `options` is an array of
   `{"id": "<id>", "value": <value>}`. The target's map and the
   result's array are two shapes of the same data. A different shape
   alone is not a mismatch.
4. Ignore result options that the target does not set.

A missing option id is a mismatch. An option id with a different
value is a mismatch. A mismatch is a failed spawn: `task_cancel` the
task, retire it, and tell the user. The recorded model is what T3
asked the provider for, not proof of what the provider served.

## Dispatch ritual

`delegate_task` delivers the task in `task` in one call. There is no
composer and no startup dialog, so there is nothing to answer and
nothing to resubmit.

1. Spawn with the task nudge in `task`, `mode: "wait"`, and
   `timeoutMs` 600000 to 900000. The call returns on completion, on
   timeout, or when the agent blocks on a question or an approval.
2. Do the model check.
3. For an implementer with `isolation: "worktree"`: call
   `t3_thread_read` on the `childThreadId` and record its
   `worktreePath` in `STATE.md`. Do not record `branch` (see
   Worktrees).
4. A result with `status` `failed` and no artifact progress is a
   failed start. Its `summary` holds the provider error. Read the
   activity for the cause before any re-dispatch.
5. Then follow the core skill's dispatch ritual.

Check the task file before the status.

## Ledger paths

The main checkout is the output of `git rev-parse --show-toplevel`,
run in your own working directory. `.overseer/` lives there. Every
ledger path derives from it.

`.overseer/` is gitignored, so a new worktree does not have it. The
agent in a new worktree starts as soon as the worktree is ready, so a
link made after the spawn is too late. Name every ledger file by its
absolute path in the main checkout:

```text
Task ready: /abs/main/checkout/.overseer/runs/<run-id>/tasks/003-rate-limit.md. Respond in that file.
```

## Reading

`t3_thread_read` has no tail offset. Read the newest N items in two
calls:

1. Get the thread's `itemCount` from `t3_thread_read` on the
   `childThreadId`.
2. Call `t3_thread_read` with `view: "activity"`,
   `afterPosition: itemCount - N - 1`, `limit: N`, and `runLimit: 1`.
   If `itemCount` is N or less, omit `afterPosition`. Never pass a
   negative value. For example, with `itemCount` 21 and N 2:

   ```json
   {"threadId": "<childThreadId>", "view": "activity",
    "afterPosition": 18, "limit": 2, "runLimit": 1}
   ```

Positions start at 0 and `afterPosition` is exclusive. This
arithmetic holds only for `view: "activity"`. The messages view has
gaps in its positions. For the health watch's "last ~30 lines" read,
use N = 10 and judge those ten items.

## Isolation

`delegate_task` has two isolation values. `shared` (the default when
the field is omitted) runs the agent in your own checkout. `worktree`
creates a new worktree from your checkout's current HEAD commit, runs
the project's setup, and binds the agent to it. There is no way to
bind an agent to an existing worktree.

Before two implementers share your checkout, run the core skill's
check:

1. Read `.overseer/active/`. Any lease but yours means worktrees.
2. Call `t3_thread_list` and look for other running threads.
3. Run `git worktree list`.
4. Run `git status` and look for changes that no agent of yours made.
5. If any check is unclear, use a worktree.

`t3_thread_list` shows only T3 threads in this project. It does not
show an agent in a terminal on the same repo, and it cannot see an
overseer running in Herdr or tmux. That run shows up only as a lease
in `.overseer/active/`. A lease whose `harness` is `t3` names a
thread you can check with `t3_thread_read`. Any other harness's
handle is not checkable here.

Spawn an implementer in your checkout by omitting `isolation`. Spawn
it in a worktree with `isolation: "worktree"`. Commit before a
worktree spawn: the worktree starts from HEAD, and uncommitted edits
in your checkout are not copied.

The reviewer, verifier, and critic always run in your checkout. Omit
`isolation` for them. When the work under review is in a worktree,
tell them the path (see Reviewing a worktree).

### Worktrees

T3 puts a managed worktree under its own directory, by default
`~/.t3/worktrees/<project>/`, and names its branch `t3/<hex>` at
creation. In the background it then generates a descriptive name
from the task and renames the branch. The rename lands minutes
later, after the agent has started. So:

- Record `worktreePath` from `t3_thread_read` at spawn. It does not
  change.
- Never record the branch at spawn. When you need it, read it from
  the tree: `git -C <worktreePath> rev-parse --abbrev-ref HEAD`.

You own the merge, as the core skill says. After the task is accepted
and reviewed, merge that branch into your checkout, then remove the
worktree with `git worktree remove <worktreePath>` and the branch
with `git branch -d <branch>`. T3's storage cleanup would remove an
idle subagent's worktree on its own schedule, but do it yourself so
`STATE.md` stays true.

### Reviewing a worktree

A reviewer, verifier, or critic runs in your checkout. When the diff
under review lives in an implementer's worktree, the agent must work
in that tree, not in its own. Put the absolute path in the nudge and
say every command runs there:

```text
Review task /abs/main/checkout/.overseer/runs/<run-id>/tasks/003-rate-limit.md. The checkout under review is /abs/worktree/path, not your working directory. Run every git and test command in that directory. Do not edit it. Write findings to /abs/main/checkout/.overseer/runs/<run-id>/review/round-1.md.
```

The probe confirmed that a Codex reviewer under full-access mode
runs scripts and writes files in a sibling worktree without a block.
Nothing in T3 stops a reviewer from editing that tree. The nudge is
the only fence. T3's diff view for that agent shows your checkout,
not the worktree. That is cosmetic.

### Replacing an implementer

A replacement for a retired or degraded implementer takes over the
old agent's tree. `task_cancel` the old task first. Then spawn the
replacement without `isolation` and name the old `worktreePath` in
the nudge the same way, with the instruction to work and commit
there. Never spawn it with `isolation: "worktree"`: a new worktree
starts without the partial work, and the resume prompt must order an
audit of that work. If the old agent shared your checkout, spawn the
replacement the same way it did.

## Questions and approvals

A spawn wait or a `task_status` read can come back with
`hasPendingQuestion` true or `pendingApproval` set. The task is still
running. The user never sees a subagent's question unless you raise
it.

For a question:

1. Call `t3_pending_request_list` with `threadId` set to the
   `childThreadId`.
2. Call `t3_pending_request_read` with the `requestId`.
3. If the task file answers it, reply with
   `t3_pending_request_respond`, with the same `threadId` and
   `requestId` and the reply in `answers`. Otherwise ask the user,
   then reply.
4. Wait again with `t3_thread_wait` on the `childThreadId` and
   `childRunId`.

For an approval: you cannot grant it. Tell the user which agent is
waiting and what it asked, and wait for them. The probe ran every
agent under the inherited `full-access` runtime mode, where no
approval is needed. Under `approval-required` or `auto-accept-edits`
an agent pauses at each action that needs one.

## On resume

The core skill's On-resume check calls `list()` and compares it with
`STATE.md`. On T3, check each handle that `STATE.md` lists as live by
its `childThreadId` with `t3_thread_read`. Use `childThreadId`, not
`taskId`: after a fresh thread takes over a run, `task_status`
rejects the old thread's task ids, and `t3_thread_read` still works.
Skip every handle that `STATE.md` marks retired. Never rebuild those.
A live agent is missing only when that read fails or shows
`archived: true`. Rebuild only those.

Use `t3_thread_list` with `includeSubagents: true` only to discover
agents that `STATE.md` does not name. Its default view leaves threads
out:

- An auto-settled thread appears only with `settled: true`.
- An archived thread appears in no view.

A `t3_thread_send` to a child of a previous overseer thread is
allowed. Wait on it with `t3_thread_wait` and the `runId` the send
returned, and record that `runId` in `STATE.md`. Do not count on a
completion wake: T3 notifies the thread that delegated the task, and
that is no longer you.

## Retiring and cleanup

A finished subagent needs no archive. It has no sidebar row, and
its card stays inside your thread as the record. Retire it by
marking it retired in `STATE.md`. A still-running agent is retired
with `task_cancel` first.

After you merge a worktree's branch, remove the worktree and the
branch as Worktrees describes.
