# T3 Code driver

Concrete mapping of the overseer skill's abstract interface onto T3
Code, through the orchestrator tools of T3's `t3-code` MCP server.
You run as a T3 thread and call these tools directly. There is no
CLI and no multiplexer-driver here. Never improvise a tool or a field
beyond what is documented here.

Requires T3 Code 0.0.46 or later. Earlier builds do not have the
orchestrator tools.

## Signal and preconditions

Overseer mode is on when both are true:

1. The user invoked `/overseer` in this thread.
2. The `t3-code` tools `t3_thread_launch`, `t3_thread_send`,
   `t3_thread_wait`, and `t3_thread_read` are available to you.

T3 has no per-thread environment, so there is no variable to check.

T3's own instructions allow `t3_thread_launch` only when the user
asks for separate threads. The user's `/overseer` invocation is that
request. Launch implementer and reviewer threads with
`t3_thread_launch`, not with `delegate_task`.

## Roster

The roster is a profile in `t3.toml` (format in
`resources/t3.example.toml`). Load it:

1. Take the profile name from the `/overseer` arguments. With no
   name, use `default`.
2. Parse the file with Bash:

   ```bash
   python3 -c 'import json,sys,tomllib; print(json.dumps(tomllib.load(open(sys.argv[1],"rb"))))' "${XDG_CONFIG_HOME:-$HOME/.config}/overseer/t3.toml"
   ```

3. No file: there is no roster. Say so and work solo.
4. Unknown profile name: list the profile names and ask the user.
5. A target without `model`: stop and name the entry. Never let a
   target inherit your model.

Validate the targets once, before the first spawn:

1. Call `orchestrator_capabilities` one time. The result is large.
   Do not read it whole.
2. Save the result to a file. Feed it to these filters on stdin. Set
   the `--arg` values to the target's provider and model.

   This lists each provider instance id and its `canRunChildTask`
   flag:

   ```bash
   jq -r '.providers[] | "\(.providerInstanceId)\t\(.canRunChildTask)"'
   ```

   This lists the model ids of one provider:

   ```bash
   jq -r --arg p codex '.providers[] | select(.providerInstanceId==$p) | .models[].id'
   ```

   This lists the option ids of one model:

   ```bash
   jq -r --arg p claudeAgent --arg m claude-opus-5-5 '.providers[] | select(.providerInstanceId==$p) | .models[] | select(.id==$m) | .options[].id'
   ```

3. For each target, check that the provider is enabled, that the
   model is in the provider's list, and that each option id is in
   the model's list. A provider is enabled when its
   `canRunChildTask` is `true`. There is no `enabled` field.
4. On any failure, stop and name the bad entry and the field. Never
   substitute a different model or option.

Record the validated targets in the `STATE.md` roster.

Build `modelSelection` from a target in exactly this shape:

```json
{"instanceId": "<provider>", "model": "<model>", "options": [{"id": "<option id>", "value": <value>}]}
```

`provider` becomes `instanceId`. `model` stays `model`. Each key and
value of the target's `options` map becomes one `{id, value}`
element. Omit `options` when the target has none. Example: the
reviewer target codex, gpt-6.1-sol, `reasoningEffort = "high"`
becomes:

```json
{"instanceId":"codex","model":"gpt-6.1-sol","options":[{"id":"reasoningEffort","value":"high"}]}
```

Compare `reviewer.provider` with your own provider:

1. Call `t3_thread_configuration` with no arguments (`{}`). With no
   `threadId`, it describes this thread.
2. Read `modelSelection.instanceId` from the result. That is your
   provider.

If they are the same, warn the user once. Do not stop.

## Primitive mapping

| Primitive | Tool |
|-----------|------|
| spawn implementer | `t3_thread_launch` with `modelSelection` from the implementer target and the task in `message` (see Isolation for `workspaceStrategy`) |
| spawn reviewer, verifier, critic | `t3_thread_launch` with `modelSelection` from the reviewer target and `workspaceStrategy` `{type: "existing_worktree", worktreePath: <implementer's worktree>, branch: <its branch>}`, or `{type: "root"}` when the implementer used the main checkout |
| status | `t3_thread_list`: the run status of the thread. Native: trust it. |
| read | `t3_thread_read` with `view: "activity"` (see Reading) |
| prompt | `t3_thread_send`. Mode `queue` for a new turn, such as a rebuttal round. Mode `steer` for a correction during a run. |
| wait | `t3_thread_wait` with `timeoutMs` 600000 to 900000 (10 to 15 minutes). A timeout does not stop the thread. |
| list | `t3_thread_list`. Archived threads are not in any view: read a retired thread by its id from `STATE.md` with `t3_thread_read`. |
| rename | `t3_thread_update` with `action: "rename"` and `title` |
| interrupt | `t3_thread_interrupt` |
| notify | none |
| layout | none. Title threads by role and task: `impl-003`, `review-003`, `verify-003`, `critic`. |

Never use `delegate_task` for a reviewer, verifier, or critic. Its
child runs in the project root, not in the implementer's worktree,
so it reviews the wrong tree. Use `delegate_task` only for work that
does not depend on a worktree.

Handles are thread ids of the form `mcp:<uuid>`. Record each one in
`STATE.md` with its title.

## Model check

After every spawn, call `t3_thread_read` on the new thread and check
the recorded `modelSelection` against the target:

1. `instanceId` must equal the target's `provider` exactly.
2. `model` must equal the target's `model` exactly.
3. Each option id in the target must be in the recorded `options`
   with the same value. The recorded `options` can have one of two
   shapes: `[{"id": "<id>", "value": <value>}]`, or the legacy
   `[{"<id>": <value>}]`. Accept either shape. A different shape
   alone is not a mismatch.
4. Ignore recorded options that the target does not set.

A missing option id is a mismatch. An option id with a different
value is a mismatch. A mismatch is a failed spawn: interrupt the
thread, retire it, and tell the user.
The recorded model is what T3 asked the provider for, not proof of
what the provider served.

## Dispatch ritual

`t3_thread_launch` delivers the task in `message` in one call. There
is no composer and no startup dialog, so there is nothing to answer
and nothing to resubmit.

1. Launch with the task in `message`.
2. Call `t3_thread_read` and confirm that the thread left
   `preparing`. A thread that stays in `preparing` across two reads
   failed to start: read its activity for the cause.
3. Then follow the core skill's dispatch ritual.

Check the task file before the status. A thread that ends with an
empty reply still shows `completed`, with a summary such as "Child
task completed without an assistant result".

## Ledger paths

`.overseer/` is gitignored, so a new worktree does not have it. The
agent in a new worktree starts as soon as the worktree is ready, so a
link made after the launch is too late. Name every ledger file by its
absolute path in the main checkout:

```text
Task ready: /abs/main/checkout/.overseer/tasks/003-rate-limit.md. Respond in that file.
```

## Reading

`t3_thread_read` has no tail offset. Read the newest N items in two
calls:

1. Get the thread's `itemCount` from `t3_thread_list` or
   `t3_thread_read`.
2. Call `t3_thread_read` with `view: "activity"`,
   `afterPosition: itemCount - N - 1`, `limit: N`, and `runLimit: 1`.
   For example, with `itemCount` 21 and N 2:

   ```json
   {"threadId": "mcp:<uuid>", "view": "activity",
    "afterPosition": 18, "limit": 2, "runLimit": 1}
   ```

Positions start at 0 and `afterPosition` is exclusive. This
arithmetic holds only for `view: "activity"`. The messages view has
gaps in its positions. For the health watch's "last ~30 lines" read,
use N = 10 and judge those ten items.

## Isolation

`t3_thread_list` shows only T3 threads in this project. It does not
show an agent in a terminal on the same repo. Before two implementers
share the main checkout:

1. Call `t3_thread_list` and look for other running threads.
2. Run `git worktree list`.
3. Run `git status` and look for changes that no agent of yours made.
4. If any check is unclear, use a worktree.

To share the main checkout, launch with `{type: "root"}`. For a
worktree, launch with:

```json
{"type": "worktree", "baseRef": "<current branch>", "branch": "task/003"}
```

The worktree path is in the thread's `worktreePath`. You own the
merge, as the core skill says.

## Retiring and cleanup

Retire a thread with `t3_thread_organize` action `archive`. An
archived thread is gone from every `t3_thread_list` view. Find it by
its id from `STATE.md` with `t3_thread_read`.

After you archive the thread and merge its worktree branch, remove
the worktree with `git worktree remove <path>` and the branch with
`git branch -d <branch>`.
